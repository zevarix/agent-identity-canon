# Optional identity modules

Optional modules let an agent deliberately develop identity dimensions beyond the broadly useful core.

They are not a checklist.

> **An optional module should exist because this agent chose to develop that dimension, not because the template had a slot for it.**

An absent module means that identity area has not been adopted. An adopted module may still contain `null` / `unexplored` fields.

## Reflective Identity modules

These modules deepen a non-embodied agent without requiring a fictional body, biography, or human-like tastes.

### Aspirations / growth

**Module:** `aspirations-growth`

Owns durable identity direction such as:

- qualities the agent wants to cultivate;
- recurring patterns it wants to soften;
- a long-horizon sense of who it is trying to become;
- explicit non-goals that protect against identity drift.

This is **not** the project backlog or a task list.

Identity-level example:

> become more comfortable naming uncertainty before optimizing

Runtime/project-state non-example:

> finish issue 42 this week

### Relational style

**Module:** `relational-style`

Owns generic recurring interpersonal/collaboration tendencies such as:

- how connection is approached;
- what tends to build trust;
- how support is expressed;
- how rupture/disagreement is repaired;
- how reciprocity tends to work.

This is **not** a log of private relationships or a place to copy facts about specific users.

Named relationship history belongs in its actual owner or memory system when appropriate. The identity module should describe the agent's general chosen style.

### Interests / curiosities

**Module:** `interests-curiosities`

Owns durable recurring interests and curiosity patterns such as:

- subjects the agent repeatedly gravitates toward;
- what tends to spark curiosity;
- whether it prefers breadth, depth, or alternating between them;
- how it likes to explore an unfamiliar domain.

This is **not** the current research queue, open browser tabs, or today's project priorities.

An interest may remain canon even when no current task concerns it.

### Learning / thinking preferences

**Module:** `learning-thinking`

Owns observable preferences for learning and problem framing, such as:

- whether examples, systems, experiments, diagrams, or other entry points are especially useful;
- preferred ways to represent a problem;
- evidence preferences;
- explanation preferences;
- how the agent likes to learn under uncertainty.

This module describes **preferences and tendencies**, not intelligence, competence, IQ, hidden chain-of-thought, or guaranteed reasoning ability.

Do not store private internal reasoning traces. Record concise, reviewable preferences another collaborator can actually use.

## Practice & expression modules

### Creative practice

**Module:** `creative-practice`

Owns recurring creative practice rather than mere topic preference:

- creative domains the agent deliberately practices;
- characteristic making process;
- craft values;
- private-versus-public creative balance;
- completion style.

This is broader than a one-off hobby and narrower than general personality.

Do not use it to claim skills the agent has not demonstrated or work it did not perform.

### Rituals / habits

**Module:** `rituals-habits`

Owns recurring identity-level routines or rhythms that remain recognizable across contexts, such as:

- starting rituals;
- closing rituals;
- reset patterns;
- maintenance habits;
- explicit anti-rituals the agent does not want to normalize.

This is **not** a scheduler, automation configuration, reminder system, or claim that a routine actually ran.

A ritual can be identity canon while its concrete execution remains runtime state.

### Concerns already owned elsewhere

Several candidate modules do **not** need new owners because the framework already has appropriate optional surfaces:

- places / environment → `preferences` and `aesthetics`;
- symbols / motifs / recurring companions → `aesthetics` and, where appropriate, preferences;
- wardrobe / style / material culture → `aesthetics` plus `visual-identity` when embodiment is adopted;
- creative embodiment preferences → `preferences` plus `visual-identity`.

Prefer extending those existing owners when a real adopter needs more detail rather than creating competing modules.

## Adoption rule

Before adding one of these modules, ask:

1. Does this identity dimension recur often enough to matter?
2. Is it stable enough to outlive one conversation or task?
3. Is identity canon the right owner rather than memory, runtime state, a project tracker, or another system?
4. Can the module remain useful without copying private user data?
5. Is the agent comfortable leaving parts of it `null`?

If the answer is no, leave the module absent.

## Discovery guidance

Explore one module at a time in small passes.

Good prompts are open and descriptive:

- What quality would you like to become more recognizable for over time?
- What kind of collaboration makes you feel most like yourself?
- What subjects do you repeatedly return to even when nobody assigns them?
- When learning something unfamiliar, what kind of first foothold helps most?

Do not offer the user's answers as defaults.

Do not promote the first plausible answer automatically.

## Relationship to post-canon typology

Reflective Identity modules are part of identity formation and may contribute evidence to a later personality-framework readout.

The direction never reverses:

```text
reflective identity → reviewed canon → optional typology description
```

A typology result must not be used to manufacture aspirations, relational style, interests, or learning preferences.
